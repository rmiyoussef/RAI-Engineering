# .brain ARCHITECTURE

> Structural authority for `.brain/`. Defines what the brain is, what lives where, how parts relate, how information flows. Operational behavior lives in `INSTRUCTIONS.md`. Navigation map lives in `INDEX.md`.

## 1. What `.brain` Is

`.brain/` is the single source of truth and central intelligence of this project. Every AI agent treats it as authoritative for project understanding, architecture, instructions, rules, constraints, planning, tasks, test cases, test results, summaries, decisions, memory, lessons, agent behavior, skills, templates, current state.

No parallel sources of truth outside `.brain/` unless strong technical reason documented in `memory/decisions/`.

## 2. Top-Level Directory Responsibilities

| Directory | Responsibility | Contains |
|---|---|---|
| `constitution/` | Immutable-ish values. Mission, principles, canonical rules R1-R45, constraints, quality bar. Changes require decision record. | `MISSION.md PRINCIPLES.md RULES.md CONSTRAINTS.md QUALITY.md` |
| `context/` | Current project facts an agent needs to ground work. Regenerated by ARCHITECT when project changes. | `PROJECT.md STACK.md ARCHITECTURE.md STRUCTURE.md ENVIRONMENT.md INTEGRATIONS.md` + gitignored `connections/` |
| `knowledge/` | What the system currently knows (timeless how-things-work). Organized by purpose, never by domain. | `architecture/ components/ database/ api/ infrastructure/ security/ patterns/` |
| `memory/` | What happened and why (historical record). Append-only; never rewrite history. | `decisions/ discoveries/ lessons/ incidents/ sessions/` |
| `plans/` | Plans with lifecycle states. Each plan is a directory named by ID. | `active/ completed/ blocked/ archived/` |
| `test-cases/` | First-class test cases grouped by owning plan ID. | `active/ completed/ failed/ archived/` |
| `summaries/` | Final summaries of completed plans. One file per plan. | `active/ completed/ archived/` |
| `agents/` | Agent definitions: role, inputs, outputs, workflow, guardrails. No project knowledge duplicated inside. | `*.md` per agent |
| `skills/` | How to perform work (reusable methods). No project-specific knowledge inside. Universal unless `domains:` frontmatter says otherwise. | `*.md` per skill |
| `rules/` | Engineering rules by purpose (organizational only, not domain brains). Hierarchy GLOBAL > CATEGORY > PROJECT > PLAN > TASK. | `coding/ architecture/ database/ api/ testing/ security/ performance/ infrastructure/ git/` |
| `reference/` | Stable protocols and external references. Rarely changes. | `message-protocol.md orchestration-protocol.md inter-session-protocol.md mantine.md ...` |
| `templates/` | Scaffolds for plans, test cases, summaries, testing modes, decisions. | `plan/ test-case/ summary/ testing/ summary/` |
| `sessions/` | Session registry (`identity.json`, gitignored `live/`). | registry only |
| `session-bus/` | Ephemeral inter-session messages. Gitignored. Never relied on as memory. | `inbox/ archive/` |
| `state/` | Lightweight machine-readable pointers to current work. No duplicated documents. | `current.yaml plans.yaml tasks.yaml tests.yaml agents.yaml version migrations.log system-manifest.sha256` |
| `_deprecated/` | Intentionally retired structures with migration reason. Read-only history. | `DOMAINS_MIGRATION.md old-domains/` |

Root files: `ARCHITECTURE.md` (this file), `INSTRUCTIONS.md` (operations), `INDEX.md` (navigation map), `README.md` (human overview), `TIMELINE.md` (generated chronological view).

## 3. Relationships Between Directories

```
constitution ──constrains──> rules ──constrains──> plans ──produces──> test-cases
     │                            │                     │                      │
     │                            │                     v                      v
     │                            │                  execution ──records──> summaries
     │                            │                     │                      │
     v                            v                     v                      v
context ──grounds──> knowledge <──updates── memory <──persists── sessions/state
     ^                    ^            ^
     │                    │            │
agents read ──────────────┴────────────┘ (never duplicate; always retrieve)
skills inform execution; templates scaffold artifacts
```

- `constitution` constrains everything. Plan/task rules add constraints but never silently violate higher rules.
- `context` + `knowledge` + `memory` ground every plan. A plan citing none of them is unjustified.
- `plans/` owns tasks. `test-cases` owns verification. `summaries` owns the record. `state` only points at them.
- `memory/decisions` explains `knowledge` (e.g. knowledge: "Redis used for queues"; decision: "chosen because DB queue latency unacceptable").

## 4. Information Flow

```
Request → load ARCHITECTURE + INSTRUCTIONS → read state/ → selective context/rules/knowledge/memory
  → plans/active/PLAN-XXXX/ (PLAN.md TASKS.md CONTEXT.md DECISIONS.md TEST-PLAN.md STATUS.md)
  → test-cases/active/PLAN-XXXX/ (TC-*.md + INDEX.md)
  → implementation (code repo, not .brain)
  → test execution records back into TC files → STATUS.md updates → state/*.yaml updates
  → summaries/completed/PLAN-XXXX.md → memory/ (decisions/discoveries/lessons) → knowledge/ (if timeless)
  → plans/completed/ + test-cases/completed/ + state/ updated
```

## 5. Agent Interaction

- Agents retrieve knowledge from `.brain`; never duplicate project knowledge inside agent files.
- Agents write only through their defined artifacts (PLANNER→plans+test strategy, EXECUTOR→code, TESTER→test cases+results, MEMORY SCRIBE→memory/summaries/state, ARCHITECT→context/knowledge).
- Message routing/validation protocol: `reference/message-protocol.md`. Parallel dispatch: `reference/orchestration-protocol.md`. Inter-session: `reference/inter-session-protocol.md`.

## 6. Lifecycles

### Planning

`active/` → (`blocked/` ↔ `active/`) → `completed/`. `archived/` holds pre-lifecycle or historical plans (see `_deprecated/` note + plan STATUS.md for provenance). Plan dir: `PLAN.md TASKS.md CONTEXT.md DECISIONS.md TEST-PLAN.md STATUS.md` (`TEST-PLAN.md` = test strategy: coverage map task→TC, required vs optional, execution order). IDs: `PLAN-0001` increasing. Next ID tracked in `state/plans.yaml`.

### Testing

Test cases live under `test-cases/<state>/PLAN-XXXX/TC-YYYY.md` + `INDEX.md`. Statuses: `PENDING RUNNING PASSED FAILED BLOCKED SKIPPED`. `failed/` holds currently-failing cases requiring fixes; resolved cases move with their plan to `completed/`. Execution recorded inside the TC file (actual result, date, executor). Required cases unresolved ⇒ plan cannot complete.

### Summary

One file per plan: `summaries/completed/PLAN-XXXX.md`. In-progress work may keep `summaries/active/PLAN-XXXX.md` draft. Pre-lifecycle historical task records live in `summaries/archived/`.

### Memory

Append-only. `decisions/` (choice + rationale + consequences), `discoveries/` (found facts), `lessons/` (what went wrong + prevention), `incidents/` (production-grade failures), `sessions/` (per-interaction log). Trivial events get no entry. Stale knowledge: corrected by new memory entry + `knowledge/` update, never by editing old files.

### Rules Hierarchy

`GLOBAL (constitution/RULES.md)` > `CATEGORY (rules/<purpose>/)` > `PROJECT (context/PROJECT.md constraints)` > `PLAN (plans/.../PLAN.md constraints)` > `TASK (TASKS.md notes)`. Specific levels add constraints; conflicts escalate to user, never silent violation.

### Knowledge Hierarchy

`reference/` (stable protocols) > `knowledge/<purpose>/` (current how-things-work) > `context/` (current project facts). Knowledge entries carry `domains:` frontmatter as metadata (e.g. `[backend]`, `[frontend]`); absence means universal. Domains never become directories.

### State Management

`state/` files are pointers, updated by MEMORY SCRIBE after each lifecycle transition. Derivable data is not stored. If `state/` disagrees with artifact locations, artifacts win; fix state.

## 7. Naming and Metadata Conventions

- Plans: `PLAN-XXXX` zero-padded, increasing. Test cases: `TC-YYYY` globally unique, each file declares `Plan:` ID. Summaries: `PLAN-XXXX.md` matching plan ID.
- Memory/decisions/lessons: `YYYY-MM-DD-slug.md`. Sessions: `YYYY-MM-DD-slug.md` with `Type:` field.
- Frontmatter `domains: [backend|frontend|devops|mobile|all]` marks technical-domain metadata on rules/skills/knowledge. Cross-cutting work lists multiple or omits the tag.
- Every plan, TC, summary cross-references the others by ID, not just by path.

## 8. Dependency Rules

- TC files depend on their plan (`Plan: PLAN-XXXX`). Plans list `Required test cases`. Summaries list `Tests executed` with results.
- TASKS.md entries link to TC IDs covering them. A task without covering TC (or explicit waiver with reason) blocks completion.
- Knowledge updates cite the decision/session that motivated them.

## 9. Inside vs Outside `.brain`

Inside: everything listed in §2. Outside (code repo): implementation code, generated build artifacts, secrets (connections stay in gitignored `context/connections/`). Test result logs may live in repo CI; the verdict + evidence summary lives in the TC file.

## 10. Retrieval (Progressive Disclosure)

Always load: `ARCHITECTURE.md`, `INSTRUCTIONS.md`. Then selectively: `state/current.yaml`, relevant `context/`, applicable `rules/<purpose>/`, relevant `knowledge/`, relevant `memory/`, active plan dir, relevant TC files. Use `INDEX.md` as the map. Never bulk-read the whole brain.

## 11. Updates and Staleness

- Agents update the brain at lifecycle transitions (plan created, TC executed, plan completed), not opportunistically mid-step.
- Stale knowledge: any agent spotting contradiction records a `discoveries/` or `lessons/` entry and flags ARCHITECT/MEMORY SCRIBE; never silently overwrites.
- Completed work becomes historical knowledge via summary → memory → knowledge promotion (MEMORY SCRIBE + ARCHITECT).

## 12. Data Ownership (System vs User Files)

A user's `.brain` is valuable project history. The migration must preserve the brain while upgrading its operating system.

### System-managed (RAI owns, update.sh may refresh)

`ARCHITECTURE.md INSTRUCTIONS.md README.md INDEX.md`, `constitution/`, `reference/`, `templates/`, `agents/`, `skills/`, `rules/`, `state/version`, `state/system-manifest.sha256`. If a user customized a system file, update.sh never silently destroys it: unchanged-since-install ⇒ safe update; user-modified ⇒ preserve original, install incoming as `.new`, record warning in `state/migrations.log`, notify user.

### User-owned (never deleted, never overwritten)

`plans/`, `test-cases/`, `summaries/`, `memory/`, `knowledge/`, `context/` (except gitignored `connections/` plumbing), `sessions/identity.json`, plus legacy equivalents discovered during migration (`tests/`, `tasks/`, `decisions/`, `notes/`, domain subtrees). Merge, never replace. If classification is uncertain, preserve the original and report for manual review.

### Ephemeral (gitignored, never memory)

`session-bus/`, `sessions/live/`, `context/connections/`, `.migration/` backups. Never relied on as knowledge; never read as project history.

## 13. Migration Principles

1. **Detect before acting.** update.sh inspects structure + `state/version` first, then dispatches: fresh install, idempotent re-run, or incremental versioned migration (`migrate_vN_to_vM`).
2. **Non-destructive by default.** No `rm -rf .brain`, no whole-tree replace, no overwrite of user files. Repeated runs are safe and produce no duplicates.
3. **Backup before structural change.** Snapshot to `.brain/.migration/backup-<timestamp>-v<old>-to-v<new>.tgz` when migration modifies user data/structure. Backups excluded from AI retrieval and from git.
4. **Log everything.** Append to `state/migrations.log`: timestamp, old→new version, migration performed, files moved/preserved, conflicts, warnings. No secrets in logs.
5. **Conflict safety.** Old file + new file + meaningful differences ⇒ keep user file, write incoming as `.new`/`.template`, warn. Never destructive assumptions.
6. **Verify before deleting source.** Migrated domain content is removed only after the new locations verify (file count + spot content). `git log --follow` preserves history across moves.
7. **Versioned and incremental.** Brain version in `state/version` (`RAI_BRAIN_VERSION=N`). Never assume upgrade-from-latest; run each pending step in order.

## 14. AI-Agent Integration (Vendor-Neutral)

The brain protocol works with any model and any compatible tool (Claude Code, OpenCode, Codex, IDE agents, future tools). No model is hard-coded; no vendor behavior is assumed (R9).

```
AI TOOL (Claude / OpenCode / Other)
   ↓
RAI ENTRYPOINT (thin adapter: CLAUDE.md, AGENTS.md, opencode config)
   ↓
.brain/INSTRUCTIONS.md → .brain/ARCHITECTURE.md
   ↓
BRAIN
```

- Entry files are thin bootstraps: "RAI installed → read INSTRUCTIONS.md → read ARCHITECTURE.md → follow workflow → treat .brain as source of truth." They never duplicate brain instructions.
- Entry behavior on plan/implement/complete requests is defined in INSTRUCTIONS.md §§3-5 (mandatory plans store, no-bypass rule, completion verification, planning thresholds).
- update.sh detects available tools (`claude`, `opencode`, ...) without failing when absent, and ensures the thin adapters exist.
